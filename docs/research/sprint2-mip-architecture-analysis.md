## 3. Literature Review

Each paper below is summarized against the fixed checklist the task specifies: problem definition, optimization objective, routing model, traffic model, assumptions, mathematical formulation, decision variables, constraints, objective function, heuristics, exact algorithms, scalability discussion, implementation implications.

### 3.1 [Fortz00] — Internet Traffic Engineering by Optimizing OSPF Weights

- **Problem definition:** given a topology, capacities, and a demand matrix, choose OSPF link weights so that OSPF's own shortest-path + equal-cost-multipath (ECMP) routing behavior performs as well as possible.
- **Optimization objective:** minimize a piecewise-linear, convex penalty function `Φ_a(load)` per link, summed over all links — a heavily-graduated congestion penalty (cost multipliers 1×, 3×, 10×, 70×, 500×, 5000× across utilization bands from <1/3 up to ≥110%), **not** a literal `min-max` MLU objective, though the steep penalty above 100–110% makes it behave like one in practice.
- **Routing model:** OSPF shortest-path routing with **ECMP even-split** — flow leaving a node toward a destination divides evenly across every outgoing link that lies on a shortest path to that destination.
- **Traffic model:** a static demand matrix, one snapshot; no prediction, no dynamics.
- **Assumptions:** directed graph; link weights are the only lever (topology and capacities fixed); routing is a deterministic function of the weight setting.
- **Mathematical formulation:** the *unrestricted* "general routing problem" (no OSPF/ECMP restriction — this is precisely Revision 1's/this revision's "OPT") **is given in full**: a linear program with per-demand, per-link continuous flow variables, flow-conservation constraints, and the piecewise-linear cost function — the paper's own Proposition 1 states this is solvable in polynomial time (citing Khachiyan). The **OSPF-restricted** problem is explicitly stated to be **not** LP-representable: *"the condition of splitting between shortest paths based on variable weights cannot be formulated as a linear program"* (§II.B) — no exact MIP formulation for it is given anywhere in the paper.
- **Decision variables (OPT LP only):** per-demand, per-link flow fraction; for OSPF weight optimization, the paper treats the weight vector as the object being searched over by its heuristic, not as MIP decision variables in a written-out formulation.
- **Constraints (OPT LP only):** flow conservation per node/demand; link cost defined via the piecewise-linear function; standard capacity coupling.
- **Objective function:** `min Σ_a Φ_a(load(a))` for the OPT LP; for OSPF weight optimization, the same cost function evaluated under OSPF-and-ECMP-induced routing, treated as a black-box function of the weight vector that the local search minimizes.
- **Heuristics:** a **local search** over weight settings, with hash tables to avoid search cycling/repetition and dynamic-graph algorithms to make re-evaluating the routing after a small weight perturbation fast. This is the paper's actual, complete algorithmic contribution for the hard (OSPF) problem — there is no exact-MIP alternative offered.
- **Exact algorithms:** only for the unrestricted OPT LP (polynomial-time, via any LP solver); explicitly **not** for OSPF weight optimization, which the paper proves NP-hard (proof itself deferred to an uncited/unsupplied journal version — see Revision 1 §C4, unchanged).
- **Scalability discussion:** the paper's efficiency contributions (hash-table cycle avoidance, incremental routing recomputation) exist specifically because local search re-evaluates *many* candidate weight settings per run — an implementation-efficiency concern, not a MIP-scale concern (there is no MIP for this problem here).
- **Implementation implications:** confirms OPT is a clean, reusable LP baseline; confirms LWO cannot be attacked exactly with an LP/MIP as simple as OPT's, and that a local-search heuristic is the literature's own answer, not a corner that this project is cutting on its own.

### 3.2 [Parham21] — Traffic Engineering with Joint Link Weight and Segment Optimization

- **Problem definition:** formalizes and relates four traffic-engineering problems over the *same* network instance: `OPT` (unrestricted flow), `LWO` (weights only, ECMP routing), `WPO` (waypoints only, weights fixed, ECMP-between-waypoints routing), and `Joint` (both weights and waypoints, jointly optimized) — and proves formal gaps between them.
- **Optimization objective:** minimize Maximum Link Utilization (MLU), literally `min z` s.t. `z ≥ util(e) ∀e` — a true min-max objective, unlike [Fortz00]'s summed penalty.
- **Routing model:** for `LWO`/`WPO`/`Joint`, flow **must** follow shortest-path links under the given weight setting, and **must split evenly** ("even-split," ES) over every outgoing link on a shortest path — i.e., true ECMP, applied recursively at every waypoint-to-waypoint leg. `OPT` alone permits arbitrary fractional splitting at any node.
- **Traffic model:** a static demand list `D` of `(s, t, d)` tuples, one snapshot, no prediction/dynamics.
- **Assumptions:** directed graph; a waypoint is a single node inserted into a demand's route; up to `W` waypoints per demand (paper's own headline analysis is at `W=1`, with generalizations to constant `W`).
- **Mathematical formulation:** `OPT`'s LP is **not written out** in this paper — deferred to reference [18] (Fenz, Förster, Parham, Schmid, Süß, the authors' own external companion report, not supplied). The exact **Joint MILP is likewise deferred to the same reference [18]**, confirmed independently from both copies of the PDF in this revision (§2). What **is** fully specified in-paper: the definitions of `OPT`/`LWO`/`WPO`/`Joint` (§2), the inequality `OPT ≤ Joint ≤ min{LWO, WPO}` (Eq. 2.1), several fully-worked lower-bound gap constructions (TE-Instances 1–5, with complete proofs including Appendix A), and two fully-specified **polynomial-time heuristic algorithms**: `LWO-APX` (Algorithm 1, an effective-capacity-based approximation for single-source-target LWO) and `GreedyWPO`/`JOINT-Heur` (Algorithms 2–3).
- **Decision variables:** conceptual, not formalized as MIP variables in-paper — a weight `w(e)` per link, a waypoint (or waypoint sequence) per demand.
- **Constraints:** likewise conceptual/definitional in-paper (§2's problem statements), not a written constraint system.
- **Objective function:** `min MLU`, stated precisely, everywhere in the paper.
- **Heuristics:** `LWO-APX` (Algorithm 1, `O(n log n)`-approximation for single-source-target instances, built on an "effective capacity" concept); `GreedyWPO` (Algorithm 3: per demand, in descending size order, try every node as a single waypoint, keep whichever most reduces MLU under the fixed weight setting — a genuinely complete, implementable, polynomial algorithm); `JOINT-Heur` (Algorithm 2: run `HeurOSPF` [Fortz00]'s local search, run `GreedyWPO` under the resulting weights, re-split demands at the chosen waypoints, re-run `HeurOSPF`) — all three are fully specified and implementable exactly as written.
- **Exact algorithms:** none for `LWO`/`WPO`/`Joint` are given in-paper (the MIP formulations are external); `OPT` is exactly solvable but its LP is likewise not reproduced here.
- **Scalability discussion:** the paper's own MILP-based evaluation (§7, "Small Networks") was only run on a single 12-node/30-link topology (Abilene) — the paper itself treats exact MILP solving as impractical beyond small instances and relies on its heuristics for the large-topology evaluation (TopologyZoo/SNDLib, up to 65 nodes).
- **Implementation implications:** confirms Revision 1's central finding (no exact Joint MILP available to us) with a second, independent copy of the source; additionally supplies enough gap-construction detail (Appendix A, TE-Instances 2–5, general-`W` bound `Ω(n log n / W)`) to build richer hand-verifiable test cases than Revision 1 had (§9).

### 3.3 [LiYeung20] / [LiYeung19] — Traffic Engineering in Segment Routing Networks Using MILP

- **Problem definition:** find a set of `≤K`-segment SR paths carrying a full traffic matrix such that MLU is minimized, explicitly supporting **both** node-SIDs (shortest-path segments) and adjacency-SIDs (single-link segments) — the paper's central critique of prior work is that node-SID-only formulations (`K-LP`) cannot select a specific member of an ECMP group and are therefore provably not optimal.
- **Optimization objective:** `min MLU`.
- **Routing model:** an SR path is a concatenation of `≤K` segments, each either a node-SID (shortest path to a node, subject to ECMP even-split at any internal bifurcation — Eq. 21/28 enforce this explicitly) or an adjacency-SID (one specific link, unambiguous, no ECMP ambiguity at all).
- **Traffic model:** static traffic matrix `[t_ij]`, one snapshot.
- **Assumptions:** a maximum segment count `K` is fixed in advance; per-demand traffic can be arbitrarily split across multiple discovered K-segment paths at the source (Algorithm 1/2's "traffic splitting at source node").
- **Mathematical formulation:** **fully specified**, in three variants: `K-LP` (older prior work, node-SID only, LP), `e2-LP` (this paper's enhancement supporting adjacency-SIDs "in part," for `K=2` only), and **`K-MILP`** (this paper's full contribution: complete binary/integer MILP supporting both SID types for general `K`), plus a scalability-motivated **`K-sMILP`** (simplified, segment-based rather than path-based, requiring an auxiliary **"voltage constraint"** mechanism to correctly bound reconstructed path length).
- **Decision variables:** `y^p_ij ∈ [0,1]` (fraction of flow `t_ij` on segment `p`); `b^p_ij ∈ {0,1}` (segment `p` used by flow `ij`); `v^p_ij ∈ Z+` ("voltage" of segment `p` for flow `ij`, K-sMILP only); path-based variants add `x^p_ij|m`/`z^p_ij|m` per explicit path `m`.
- **Constraints:** flow conservation over the segment graph (Eq. 26); link capacity (Eq. 27); ECMP equal-split enforcement among node-SID-internal bifurcations (Eq. 21/28); segment-usage-indicator linkage (Eq. 29); and, for `K-sMILP`, the voltage-propagation system (Eqs. 30–32) that bounds the longest reconstructible path to `≤K` segments — this is **not** a simple link-count sum (see §6.3/Revision 1 §E for why a naive `Σ y(e) ≤ K` is wrong).
- **Objective function:** `min θ` (MLU), with capacity constraints scaled by `θ`.
- **Heuristics:** none of consequence — the paper's contribution is the exact formulations themselves (`e2-LP`, `K-MILP`, `K-sMILP`); the "simplified" MILP trades completeness (a segment-based solution isn't always exactly reconstructible into a valid path-based one) for tractability, not by heuristic search but by relaxing the model's fidelity.
- **Exact algorithms:** `K-MILP`/`K-sMILP`, solved directly by a MILP solver — no local search or approximation is proposed for the core contribution.
- **Scalability discussion:** `K-MILP` is `O(M·|P|·|N|²)` variables/constraints where `|P| ≈ |N|²` and `M` (max K-segment paths per node pair) is `O(|N|^{K−1})` — **exponential in K**; `K-sMILP` reduces this to `O(|P|·|N|²)`, polynomial in `|N|` and independent of `M`, at the cost of the reconstruction-completeness gap above.
- **Implementation implications:** this remains the only source with a complete adjacency-SID-aware exact formulation; it is explicitly a **V2** concern (Revision 1's assessment, unchanged) given the schema change (a SID-type concept Sprint 1 doesn't have at all) and the exponential-in-K variable count.

### 3.4 [Brundiers23] — Preprocess your Paths

- **Problem definition:** survey and comparative evaluation of techniques to reduce the size of the candidate-SR-path search space *before* handing a problem to an LP/MILP solver, so that SR TE optimization remains usable at real ISP scale.
- **Optimization objective:** `min θ` (MLU) — reproduces, and explicitly attributes, the base "2SR" LP from Bhatia, Hao, Kodialam, Lakshman, INFOCOM 2015 (**not** one of our six core papers, but its formulation is fully reproduced here as "Problem 1," so it is transitively available to us).
- **Routing model:** the *original* 2SR LP (Bhatia et al. 2015, as reproduced here) uses continuous, **arbitrarily splittable** `x^k_ij` per middlepoint `k`; the paper explicitly notes that *"newer variations... generally prohibit splitting demands over multiple SR paths by making the `x^k_ij` binary variables"* because arbitrary splitting is not practically deployable — citing further work, not proposing this itself.
- **Traffic model:** static per-topology demand matrices (Repetita dataset + a real Tier-1 ISP dataset), one snapshot per optimization run; no explicit temporal modeling (contrast with [Le21], §3.5).
- **Assumptions:** middlepoints are drawn from the full node set unless a preprocessing technique restricts them; the paper studies four specific, independently-sourced preprocessing techniques.
- **Mathematical formulation:** the base 2SR LP ("Problem 1": `min θ`; `Σ_k x^k_ij = 1`; `Σ t_ij g^k_ij(e) x^k_ij ≤ θc(e)`) is given in full; the four preprocessing techniques are each given as precise, checkable rules (not full MILPs of their own): centrality-based restriction (GSP centrality formula, Eq. 5), Stretch-Bounding (ratio bound, Eq. 6), Demand Pinning (a sorting/thresholding procedure), and SR Path Domination (a formal per-link-load domination/equivalence relation, Eq. 7).
- **Decision variables/constraints/objective:** as above — this is the one paper in our set whose primary contribution is *outside* the variables/constraints/objective triad; its contribution is a *pre-filter* applied before that triad is ever built.
- **Heuristics:** three of the four techniques (centrality, stretch-bounding, demand pinning) are heuristic/lossy by construction — proven, in the paper's own evaluation, to trade solution quality for speed.
- **Exact algorithms:** the fourth technique, **SR Path Domination**, is proven lossless (*"dominated SR paths are never needed for an optimal solution"*) — the only exact/optimality-preserving technique of the four.
- **Scalability discussion:** this is the paper's whole subject — candidate-path counts of `O(|V|^{k+1})`, unmitigated LP solve times reaching *"multiple hours or even days"* on large topologies, and the paper's own combined-preprocessing result reducing computation time by "a factor of 10 or more" without material quality loss.
- **Implementation implications:** confirms the arbitrary-vs-unsplittable modeling tension already flagged in Revision 1 (§G), now further corroborated in an even stronger form by [Le21] (§3.5, below) — three independent papers ([Brundiers23]'s citations, [Le21] directly, and Sprint 1's own existing product decision for `TrafficDistribution`) converge on "arbitrary continuous splitting is not what gets deployed."

### 3.5 [Le21] — Multi-time-step Segment Routing based Traffic Engineering Leveraging Traffic Prediction *(new in Revision 2)*

- **Problem definition:** traffic engineering via **2-Segment Routing** (one optional intermediate/waypoint node per demand), extended across a *routing cycle* of `T` future time-steps using traffic prediction, so that the routing policy does not need to be recomputed (and hence traffic does not need to be rerouted) every single time-step.
- **Optimization objective:** `min θ` (MLU) for the base single-snapshot problem `P0`; the multi-time-step variants `P1`/`P2`/`P3` minimize the **worst-case** MLU over a whole future window, under progressively looser (and cheaper-to-predict) traffic-summarization assumptions.
- **Routing model — the single most important new fact for this revision:** *"in contrast with [Bhatia et al. 2015]'s problem, we do not consider that the traffic flows can be arbitrarily split and routed by different paths"* (§II, explicit, direct quote). Each demand `(i,j)` selects **exactly one** intermediate node `k` (binary `α^k_ij`, with `Σ_k α^k_ij = 1`); the traffic from `i` to `k` and from `k` to `j` is each routed via **the** shortest path between them (a fixed, precomputed, single path — the paper never discusses ECMP, ties, or multiple equal-cost paths anywhere in its text, confirmed by an explicit full-text search). `k = i` or `k = j` degenerates to plain single-shortest-path routing with no waypoint at all — structurally the same "no waypoint" degenerate case Sprint 1's own `sanitize_segments` already normalizes to.
- **Traffic model:** the paper's genuine novelty — a sequence of **predicted** traffic matrices `M = [M_1, ..., M_T]` for the next `T` time-steps of a "routing cycle," obtained from an external, separately-trained deep-learning predictor (Graph WaveNet, cited as [12]), not computed by this paper's own optimization.
- **Assumptions:** undirected graph `G=(V,E)`; centrally-controlled (SDN-style) network; prediction accuracy is treated as an input the TE model must be robust to, not something the TE model itself controls.
- **Mathematical formulation:** **fully specified and complete** for all four problem variants:
  - **`P0`** (single time-step, the one directly relevant to Sprint 2 V1's WPO scope): `minimize θ`; `Σ_k α^k_ij = 1 ∀i,j`; `Σ_ij Σ_k g^k_ij(e) α^k_ij m^t_ij ≤ θc(e) ∀e`; `α^k_ij ∈ {0,1}`. Here `g^k_ij(e) = f_ik(e) + f_kj(e)`, with `f_ik(e) ∈ {0,1}` a **precomputed constant** (not a decision variable) indicating whether link `e` lies on the single fixed shortest path from `i` to `k`.
  - **`P1`** extends `P0`'s capacity constraint to hold at **every** time-step `t ∈ T` simultaneously, using the actual (predicted) matrix at each step — requires predicting all `T` full matrices.
  - **`P2`** relaxes `P1` to use only the **per-flow maximum** predicted demand over the whole window (`max_{t∈T} m^t_ij`) — requires predicting only one (max-value) matrix, not `T` of them.
  - **`P3`** is `P2` applied per sub-period (`T` split into `P` sub-periods of length `T_p < T`), trading some of `P2`'s prediction-simplicity back for tighter per-period bounds.
  - A proven ordering **`θ1* ≤ θ3* ≤ θ2*`** (Theorem 1/2, with a full proof, including a derived performance-ratio upper bound `λ` for `P2` vs. `P1`) formally relates the four variants' optimal objective values.
- **Decision variables:** `α^k_ij ∈ {0,1}` (which single node, if any, is the waypoint for demand `ij`); `θ ∈ R` (the MLU epigraph variable). No continuous flow-splitting variable exists anywhere in this formulation — a deliberate, stated departure from the 2015 Bhatia et al. LP it builds on.
- **Constraints:** demand-satisfaction-via-exactly-one-waypoint (`Σ_k α^k_ij = 1`); capacity/MLU-bounding, in one of four forms depending on `P0`–`P3`.
- **Objective function:** `min θ`, identical in structure to [Parham21]'s and [Brundiers23]'s MLU objectives, but over a provably different (unsplittable) routing-restriction set.
- **Heuristics:** **`LS2SR`** (Algorithm 1) — an improvement-based local search seeded from plain shortest-path routing, which at each iteration (a) probabilistically selects a heavily-loaded link (probability `∝ load(e)^β`, Eq. 27), (b) probabilistically selects a large flow crossing it (probability `∝ demand^γ`, Eq. 28), and (c) reroutes that flow to the next-more-expensive candidate path in a precomputed, **deduplicated** path list (equivalent paths and non-simple/looping paths explicitly pruned first, §IV-A) — explicitly adapted from Gay, Hartert & Vissicchio's SRLS algorithm (INFOCOM 2017, cited [3], not independently in our source set but described completely enough here to use).
- **Exact algorithms:** the paper's own experiments **solve `P0`–`P3` to optimality directly**, using the **PuLP** library (cited [15] — `pulp`, the same library recommended in Revision 1 and here) as the MILP solver, on three real backbone datasets: Brain (9 nodes/14 links), Abilene (12 nodes/15 links), and Geant (22 nodes/36 links) — a solve-time budget of 60 seconds was used for the exact solves in their experiments.
- **Scalability discussion:** the paper states plainly, citing Gay/Hartert/Vissicchio, that *"traditional MILP solvers hardly scal[e] to large topologies with more than 20 nodes"* — which is why `LS2SR` exists at all, targeting **sub-second** re-solves for the *repeated, per-cycle* multi-time-step re-optimization use case specifically, not because the single-snapshot `P0` MILP itself is intractable at their scale (their own experiments solve it directly, successfully, on a 22-node topology).
- **Implementation implications:** this is the single most consequential new source for Sprint 2's actual architecture (§6–§9 below) — it hands us a complete, validated-at-real-scale, exact ILP for precisely the "one optional waypoint" problem, using precisely the single-shortest-path-per-leg routing model Sprint 1 already implements.

### 4.2 Where assumptions differ, and why it matters for Sprint 2

| Axis | [Fortz00] | [Parham21] | [LiYeung20]/[19] | [Brundiers23] | [Le21] |
|---|---|---|---|---|---|
| **ECMP assumption** | Yes, mandatory (OSPF-defined) | Yes, mandatory, applied at every waypoint leg | Yes, within a node-SID segment (Eq. 21/28) | Inherited from whichever base LP it's preprocessing (arbitrary-split by default) | **No** — explicitly rejected in favor of single-path routing |
| **Shortest-path assumption** | Yes (weight-determined) | Yes (weight-determined, between waypoints) | Yes (node-SID = shortest path) | Yes (middlepoint legs are shortest paths) | Yes, but **exactly one** shortest path per leg, no tie-handling discussed |

### 4.3 The one genuine, explicit disagreement worth flagging as a disagreement

[Parham21]'s `WPO`/`Joint` and [Le21]'s `P0`–`P3` are **answering superficially the same question** ("what's the best single waypoint per demand to minimize MLU?") **under two different, incompatible routing models** — one even-split-ECMP-between-waypoints, one strictly single-path-unsplittable — and neither paper cites or acknowledges the other (they are contemporaneous, 2021, from unrelated research groups). Nothing in either paper's own text resolves this; it is a genuine, standing disagreement in the literature about what "waypoint optimization" routing semantics should be, and Sprint 2 must pick one deliberately rather than average or ignore the difference. §6.3/§9 record the recommendation and why.

## 5. Joint MILP Analysis

Answering the task's five specific questions, directly:

1. **Is the full mathematical formulation of the Joint (link-weight + waypoint) MILP present in our materials?** **No.** Both available copies of [Parham21] (`conext21te.pdf` and `3485983.3494846.pdf`, confirmed independently identical in this respect) state, verbatim: *"The MILP formulation of Joint is presented in [18]"* — and reference [18] in the paper's own bibliography is *"Thomas Fenz, Klaus-Tycho Förster, Mahmoud Parham, Stefan Schmid, and Nikolaus Süß. Traffic engineering with joint link weight and segment optimization. September 2021. https://whatif-tools.net/segment-routing"* — the authors' own external companion report/website, not a paper in `docs/research/papers/` and not otherwise available to us.
2. **Are all decision variables defined?** Only informally/conceptually (§2's prose definitions of a weight setting `w: E → R+` and a waypoint setting `π: D → V`) — no formal MIP variable list (e.g. no `α[k,i,j]`-style binary array) is written out anywhere in either copy of the paper, including Appendix A (which contains only gap-theorem proofs, confirmed by a full read of Appendix A in this revision — §3.2).
3. **Are all constraints available?** No — see above; only the *problem definitions* and the *inequality relating the four problems* (`OPT ≤ Joint ≤ min{LWO, WPO}`) are given, not a constraint system.
4. **Is the objective function explicitly specified?** Yes, at the level of "minimize MLU" — this part is unambiguous and consistent across the whole paper — but an objective statement alone does not make a MILP implementable without its variables and constraints.
5. **Is it sufficient for implementation?** **No.** What Sprint 2 has, from [Parham21] alone, is enough to implement **the two fully-specified heuristics** (`GreedyWPO`, `JOINT-Heur`) — genuinely useful, genuinely citable, genuinely implementable — but **not** enough to implement an exact Joint MILP solver. This conclusion is unchanged from Revision 1, now confirmed by a second independent copy of the paper and a full read of its Appendix A.

**What Revision 2 adds beyond re-confirming this gap:** [Le21]'s `P0` (§3.5) is a complete, exact MILP — but it is a formulation for **waypoint selection only, weights fixed and given** (structurally, [Parham21]'s `WPO`, not `Joint` — [Le21] never treats link weights as decision variables anywhere in its text). It does **not** fill the Joint-MILP gap; it fills a different, adjacent gap (an exact WPO-class formulation), which Revision 1 also lacked (Revision 1 only had `GreedyWPO`, a heuristic, for this). **Do not conflate the two:** Sprint 2 can now offer an *exact, provably optimal* "Optimize Waypoints" mode (via [Le21]'s `P0`, weights fixed), but "Joint Weights + Waypoints" remains achievable only as the heuristic composition [Parham21] itself proposes (`JOINT-Heur`), never as a proven-optimal MILP solve, with our current sources.

## 6. Architecture Re-evaluation

Re-examined against the full literature review above, item by item, exactly as the task requests.

### 6.1 Routing model

**No change to the four-mode taxonomy** (OPT / LWO / WPO / Joint) from Revision 1 — it remains the correct way to avoid the "everything is just MIP" conflation the whole project is trying to avoid. **One refinement**: WPO now has *two* candidate reference models in our literature ([Parham21]'s even-split, [Le21]'s unsplittable single-path), and Sprint 2 must pick one, explicitly, rather than silently blend them (§6.3).

### 6.2 ECMP handling

**Unaffected for LWO.** [Fortz00]/[Parham21] both mandate ECMP even-split for LWO, and Sprint 1's `ecmp.py` already implements exactly this (`sorted(nx.all_shortest_paths(...))`, confirmed unchanged since Revision 1 — see §7). Any Sprint 2 LWO module should keep evaluating candidate weight settings by re-running (or re-deriving from) this same ECMP logic, exactly as Revision 1 recommended.

### 6.3 Segment Routing assumptions & waypoint handling — **the central update of this revision**

Revision 1 concluded Sprint 1 SR is "single-path waypoint routing," diverging from [Parham21]'s even-split model, and recommended the Sprint 2 optimizer build its **own**, separate, even-split-aware internal routing subroutine for WPO/Joint rather than reuse Sprint 1's `resolve_segment_route` — specifically to avoid inheriting a routing-model mismatch.

With [Le21] now available, this recommendation is **reversed, with reasoning**:

- [Le21]'s `P0` is a complete, real-scale-validated, exact MILP for *exactly* "one optional waypoint per demand, single shortest path per leg, unsplittable" — which is *precisely* what Sprint 1's `resolve_segment_route` already computes (§7 confirms the code is unchanged).
- Building WPO against [Le21]'s model instead of [Parham21]'s therefore means the optimizer's routing assumption and Sprint 1's simulator's routing assumption become **the same assumption**, not two different ones needing careful separation.
- The practical consequence: the optimizer's precomputed constant `f_ik(e)` (whether link `e` lies on the shortest path from `i` to `k`, in [Le21]'s notation) should be computed by **calling `routing_helpers.resolve_segment_route`/the underlying single-shortest-path resolution directly**, not by re-implementing shortest-path logic inside the optimization module. This is both less code and — more importantly — guarantees that a WPO recommendation, when written back into Sprint 1 (`SegmentRoutingPolicy.segments`) and re-simulated, reproduces the *exact* MLU the optimizer reported, because it is the same underlying path-resolution call in both places.
- **This is a genuine reversal of a Revision 1 recommendation, made because new evidence (a complete, validated MILP over the matching routing model) became available — not a preference change.**

The one thing this does **not** resolve: [Le21]'s own formulation, like Sprint 1's, never discusses what happens when `i→k` or `k→j` has *multiple* equal-cost shortest paths — both simply call "the" shortest path and move on. This is a shared, not a new, latent assumption, and it is the subject of §7's compatibility finding and §8's PR0.

### 6.4 MLU computation

**Unchanged, unaffected, still fully reusable.** `Metrics.compute_summary()` computes exactly the `max(utilization)` quantity every paper in this literature calls MLU/`θ`/`z`. No paper introduces a different MLU definition that would require changing this function.

### 6.5 Shortest-path computation

**Directly addressed by §6.3 above** — the recommendation is now to have the optimizer's WPO/Joint modules call into the *same* shortest-path resolution Sprint 1 already exposes (`routing_helpers.resolve_segment_route`, and by extension whatever single-path primitive it's built from), rather than parallel-implementing it, as previously recommended for the (now de-prioritized) even-split model.

### 6.6 Optimization flow

**Unchanged from Revision 1's proposed sequence** (build effective graph via `GraphBuilder.build_graph()` → solve OPT → solve LWO/WPO/Joint as separate modes → project into a `SimulationResult`-shaped `OptimizationResult` for reuse by `ComparisonPanel`). [Le21] does not suggest a different pipeline shape for the single-snapshot case; its multi-time-step machinery is explicitly out of scope (§6.8).

### 6.7 Decomposition strategy

**One addition, not a change:** [Le21]'s Theorem 1/2 (`θ1* ≤ θ3* ≤ θ2*`, with a derived performance-ratio bound) is a clean, fully-proven example of *why* a looser, cheaper-to-compute problem formulation (`P2`, using only per-flow maxima) can be justified as "good enough" relative to a tighter, more expensive one (`P1`, using every time-step) — this is a useful, citable pattern for *any future* decision to trade formulation fidelity for tractability, but it is explicitly a **multi-time-step** result and does not change how Sprint 2 V1's single-snapshot OPT/LWO/WPO/Joint modes should be decomposed relative to each other (still: independent modes, not a pipeline where one feeds the next, except `JOINT-Heur`'s own internal LWO→WPO→LWO composition, unchanged from Revision 1).

### 6.8 What did *not* change

- Solver/library analysis (Revision 1 §H) — **strengthened, not changed**: [Le21]'s own experiments used PuLP successfully for exactly this problem class at 9–22-node real-backbone scale, which is direct, independent, real-world confirmation of the PuLP+CBC recommendation, not just a licensing/reproducibility argument as in Revision 1.
- The `OptimizationResult` contract (Revision 1 §J) and infeasibility terminology (Revision 1 §K) — unaffected; [Le21]'s own `θ` variable maps onto `OptimizationResult.objective` with no change needed, and its solver is used to solve to proven optimality within a time budget, which is exactly the `OPTIMAL` vs. `TIME_LIMIT` distinction Revision 1 already designed for.
- The pptx constraint audit (Revision 1 §E) — unaffected (the deck is not a source in this revision, §2).
- Node-SID/adjacency-SID analysis (Revision 1 §F) — unaffected; [Le21] does not engage with adjacency-SIDs at all, consistent with its single-path (no-ECMP-ambiguity) model needing no such disambiguation mechanism in the first place.
- TE policy compatibility mapping (Revision 1 §M) and failure compatibility (Revision 1 §N) — unaffected by any new source; [Le21]'s multi-time-step framing is the closest any paper comes to Sprint 1's PR6 scheduled-failure feature, and it remains, as Revision 1 already anticipated, **out of Sprint 2 V1's scope** (§6.9) — now confirmed against the actual paper rather than only against an unverifiable secondhand slide-deck description.

### 6.9 Multi-time-step / predictive optimization — now confirmed out of scope, with the actual paper in hand

Revision 1 treated "Multi-time-step SR TE leveraging traffic prediction" as an unverified rumor (only the deck's, since-falsified, author attribution was available). With [Le21] now fully read: **the paper is real, its formulation is real and complete, and it is exactly the kind of specialization Revision 1 predicted it might be** — a genuinely different problem (optimizing a *routing cycle* against *predicted* future traffic, requiring an external ML traffic predictor as a hard dependency) layered on top of the same single-snapshot MLU-minimization core. **Recommendation unchanged, now on firmer ground:** Sprint 2 V1 does not attempt multi-time-step or predictive optimization. If ever revisited, [Le21] is now a fully-available, fully-read source for it — cited here explicitly so a future sprint does not have to re-locate or re-verify it.

## 7. Sprint 1 Compatibility Review

**Confirmed via direct re-inspection that no Sprint 1 code changed between Revision 1 and Revision 2** (`git log`/`git diff` show no commits to `backend/app/*` or `frontend/src/*` since Revision 1's commit `0396809`). Every finding below is against the *current, unmodified* code.

### 7.1 Segment Routing semantics — re-verified, conclusion updated

`app/utils/routing_helpers.py`'s `resolve_segment_route()` still calls `nx.shortest_path(graph, waypoints[i], waypoints[i+1], weight="weight")` — **exactly one path per leg**, no ECMP, no splitting, confirmed identical to Revision 1's reading.

**Revision 1's framing** ("this is a compatibility gap against [Parham21], to be fixed later or worked around") **is superseded.** With [Le21] available: **Sprint 1's SR routing model matches [Le21]'s `P0` routing model, term for term** — one optional waypoint, one fixed shortest path per leg, no splitting. It does **not** match [Parham21]'s even-split model, and Revision 1 was right about that specific mismatch — but Revision 1 did not yet know a legitimate, complete, real-scale-validated *alternative* research model existed that Sprint 1 already happens to match. **Conclusion: Sprint 1 SR needs no architectural change to serve as the routing-model target for an exact WPO MILP, provided Sprint 2 adopts [Le21]'s model (recommended, §6.3/§9) rather than [Parham21]'s.**

### 7.2 ECMP behavior — unaffected, still compatible

`app/algorithms/ecmp.py`'s `sorted(nx.all_shortest_paths(demand_graph, ...))` remains exactly the even-split, tie-stable behavior [Fortz00]/[Parham21] require for LWO. No paper read in this revision changes this assessment.

### 7.3 Shortest-path selection — the one real, newly-precise compatibility risk

Both Sprint 1's `resolve_segment_route` and [Le21]'s `f_ik(e)`/`f_kj(e)` precomputation rely on "the" shortest path between two nodes being well-defined, when in fact — on any topology with a tie (multiple equal-cost shortest paths) — **which** path is returned depends on NetworkX's internal Dijkstra tie-breaking, which is not a documented, stable public contract (this exact caveat was already raised in Revision 1 §B.2, in the context of Sprint 1's own internal consistency; it now matters *additionally* as a **cross-module contract** between the simulator and the optimizer). Concretely: if the optimization module (§6.3, recommended to reuse `resolve_segment_route`) is called once to precompute `f_ik(e)` constants for the ILP, and Sprint 1's simulator later independently re-resolves the same route to display/verify the result, **both calls must return the identical path** for the reported MLU to be reproducible — which they will, *in the same process, on the same NetworkX version, on a graph with no structural changes in between*, but this has never been asserted or tested, only assumed. **This is the one concrete "Sprint 1 needs a small adjustment before Sprint 2" finding**, and it motivates PR0 (§8) — not a routing-model change, a **determinism guarantee**.

### 7.4 What Sprint 1 does *not* need before Sprint 2

- No change to `resolve_segment_route`'s algorithm.
- No change to `ecmp.py`, `distance_vector.py`, `GraphBuilder`, or `Metrics`.
- No new SID-type concept (adjacency-SID) — still correctly deferred to a V2 that may never happen (§3.3/Revision 1 §F, unaffected).
- No change to `TrafficDistribution`/`SegmentRoutingPolicy`/`TrafficEngineeringPolicy`/`SimulationFailureEvent` schemas — all remain directly reusable as designed in Revision 1 §A.3, unaffected by anything read in this revision.

## 11. Addendum — PR0 implemented routing contract

**This addendum records what was actually built for PR0 and how it relates to (and, in one place, overrides) §6.3/§7's analysis above. It does not rewrite those sections — they remain an accurate record of the reasoning at the time §6–§10 were written.**

§6.3 and §7.1 above analyzed two candidate WPO/SR routing models — [Parham21]'s even-split-between-waypoints and [Le21]'s unsplittable-single-path — and recommended adopting [Le21]'s model specifically *because* it required no change to Sprint 1's `resolve_segment_route`. **PR0, as actually scoped and implemented, made the opposite choice**: Segment Routing itself was upgraded to ECMP-within-segments — every leg (source→waypoint, waypoint→waypoint, last waypoint→destination) now discovers *all* equal-cost shortest paths and splits the traffic arriving at that leg's source evenly across them, exactly matching [Parham21]'s routing model rather than [Le21]'s. This is a deliberate product decision made after §6–§10 were written, not a continuation of this document's own recommendation — recorded here explicitly rather than silently reconciled.

**What changed in the code** (`backend/app/algorithms/segment_routing.py`, `backend/app/utils/routing_helpers.py`):

- New shared, algorithm-agnostic primitives in `routing_helpers.py`: `resolve_equal_cost_paths` (all shortest paths, deterministically sorted), `compute_equal_split_path_shares` (equal ECMP split), and `compute_ecmp_leg_distribution` (both together, plus per-link load contributions) — the same "what ECMP flow is induced between X and Y" question §I's `waypoint_optimizer.py` module was already meant to be able to ask, now factored out one PR earlier than planned and already exercised by a real caller (Segment Routing itself), not just a stub.
- `ECMPAlgorithm`'s own equal-cost path discovery now calls `resolve_equal_cost_paths` instead of an inline, duplicate `sorted(nx.all_shortest_paths(...))` — a pure refactor (confirmed byte-identical via the full pre-existing test suite), done specifically so Segment Routing's new leg-splitting logic and ECMP's own path discovery share one implementation rather than two.
- `SegmentRoutingAlgorithm._route_demand` now resolves every leg's ECMP distribution *before* narrating or accounting for any of them (conservation: a demand that turns out to be unreachable at a later leg must not have partially added load from earlier legs it already resolved), then materializes the full end-to-end Cartesian product of leg paths as multiple `PathShare` entries per demand — reusing `PathShare`'s existing multi-entry shape (ECMP has always used exactly this), so every piece of algorithm-agnostic code that walks `pathResults[].paths[].nodes` keeps working unmodified.
- A new trace event, `SEGMENT_ECMP_SPLIT`, narrates a leg's equal-cost split (mirroring ECMP's own `PATH_DISTRIBUTION` event) whenever a leg actually has more than one path — a leg with a unique shortest path produces the same trace shape as before PR0.

**Consequence for §7.3's "shortest-path selection" compatibility risk:** that risk (two independent callers of "the" shortest-path resolution needing to agree) is now resolved differently than §7.3 anticipated — rather than the *optimizer* needing to reuse Sprint 1's single-path resolution, Sprint 1's own SR engine now resolves *every* equal-cost path per leg deterministically (`resolve_equal_cost_paths` always returns a lexicographically sorted list), so there is no remaining "which arbitrary path did NetworkX pick" ambiguity inside Segment Routing itself. §7.3's originally-recommended PR0 (a determinism regression test on the old single-path `resolve_segment_route`) is superseded by this stronger guarantee for SR specifically; `resolve_segment_route` itself is untouched and still used by `ECMPAlgorithm`'s own `REQUIRE_WAYPOINT` special case, where the original single-path caveat still applies unchanged.

**Consequence for §6.3/§9's WPO-model recommendation:** now that Sprint 1 SR matches [Parham21]'s even-split model instead of [Le21]'s, a future Sprint 2 WPO optimizer that wants its recommendations to reproduce identically when simulated by Sprint 1 should score candidate waypoints under **even-split ECMP routing** (matching `compute_ecmp_leg_distribution`, now available as a shared primitive) — not [Le21]'s unsplittable `P0` MILP as §6.3 recommended. [Le21]'s `P0` remains fully valid as an *exact, real-scale-validated MILP* for the unsplittable model; it is simply no longer the model that matches Sprint 1's simulator after PR0. Re-deciding WPO's target model in light of this is left to the PR that actually implements it (§8's PR3), not decided here.

**Scope confirmation:** PR0 changed only Segment Routing's own routing model and the shared path-discovery helper ECMP was refactored to reuse (behaviorally unchanged for ECMP). No optimization code, solver dependency, or `OptimizationResult`/`SolverAdapter` scaffolding was added — §8's PR1–PR6 sequence is otherwise unaffected by this addendum and still describes the next work.

## 12. Addendum — PR1 implemented Optimization Framework

**This addendum records what PR1 actually built: the optimization package scaffolding plus its first mode, OPT (unrestricted optimal flow). It does not rewrite §8's PR1 table row above — that row's `POST /optimize` route and `optimization_service.py` are deliberately deferred (see below); everything else it describes was built as planned.**

**Model implemented — exactly §C1 in Revision 1, unaffected by Revision 2's re-review:** a standard multi-commodity flow LP. Decision variables are per-arc, per-demand flow amounts `f(u,v,k) ≥ 0` (continuous); constraints are flow conservation (one equality per demand per node) and capacity (one inequality per physical link); objective is `min θ` s.t. `Σ_k f(e,k) ≤ θ·capacity(e)` for every link `e` — the epigraph-form MLU linearization, algebraically equivalent to `utilization(e) ≤ θ` but avoiding division inside the constraint. No waypoint, ECMP, or shortest-path restriction is present anywhere in this model — traffic may split arbitrarily, at any node, exactly as [Parham21]/[Fortz00] define OPT.

**A correction to Revision 1's §S risk table, found empirically while building this LP, not inferred:** §S speculated that `GraphBuilder` gives an undirected link "two independent directed capacity constraints (one per direction)". This is **false** — verified two independent ways before writing any constraint code: (1) directly inspecting `GraphBuilder.build_graph()`'s output for a single undirected link, which produces exactly **one** `networkx.Graph` edge (not two); (2) running `ECMPAlgorithm.run()` with two opposing 6-unit demands over one undirected, capacity-10 link, which produced a combined load of **12** and utilization **1.2** — i.e. both directions' traffic sums into one shared capacity pool. The OPT LP is built accordingly: an undirected link contributes **two** directed flow-arc groups (one per direction, since flow direction still matters for per-node conservation) that share **one** combined capacity constraint (`Σ` over both directions, over every commodity, `≤ θ·capacity`) — never two independent per-direction constraints. `test_l_undirected_link_shares_one_capacity_pool_both_directions` in `test_unrestricted_optimizer.py` pins this behavior down as a regression test. §S's original v1 text is left as-is (historical record); this correction lives here, not there.

**Package layout** (`backend/app/optimization/`, matching this PR's own suggested naming rather than §8's original `{models,solver,result}.py`/`opt_flow.py` sketch, since the finer split below turned out cleaner once actually implemented):
- `models.py` — `OptimizationResult`, `FlowAssignment`, `OptimizationStatus`, `OptimizationMode` (currently `Literal["OPT"]`, to be widened by PR3/PR4/PR5).
- `solver_adapter.py` — `SolverAdapter` (abstract) + `PulpCbcAdapter` (the only concrete adapter; wraps PuLP's bundled `PULP_CBC_CMD`). This is the *only* file that imports a PuLP solver class directly — every optimizer builds its model against PuLP's own modeling API (`LpProblem`/`LpVariable`/`lpSum`) directly, since PuLP already is a solver-agnostic modeling layer and a second DSL on top of it would be pure overhead (§H/§I in Revision 1, reaffirmed here after actually building it).
- `objective.py` — `add_mlu_objective`, the `min θ` epigraph objective every future mode (WPO/LWO/JOINT) will reuse verbatim.
- `constraints.py` — `add_flow_conservation_constraints`, `add_capacity_constraints`: the general multi-commodity-flow constraint vocabulary.
- `utils.py` — `build_optimization_topology` (turns `GraphBuilder`'s existing output into LP-ready arc/capacity-group structures — no second topology representation) and `decompose_flow_to_paths` (turns the LP's raw per-edge flow solution back into explicit weighted paths for `flowAssignments`, via standard flow decomposition: repeatedly extract a source→target path through positive-remaining-flow arcs, subtract its bottleneck, repeat; any leftover flow-cycle residue is discarded as carrying no net demand).
- `unrestricted_optimizer.py` — `solve_unrestricted_optimum(network, time_limit_s=None, solver=None) -> OptimizationResult`, composing the above.

**`OptimizationResult` field reconciliation:** PR1's own spec lists `status, objectiveValue, mlu, linkLoads, linkUtilizations, flowAssignments, solverRuntime, optimalityGap, solverName, message` — implemented verbatim, with three additive fields carried over from Revision 1's Part J design because every future mode will need them too: `mode` (`"OPT"` for this PR), `lowerBound` (populated for `OPTIMAL`; an LP has no branch-and-bound gap, so `lowerBound == objectiveValue` whenever `status == "OPTIMAL"`), and `debugInfo` (matching `SimulationResult`'s own field of the same name/purpose). `objectiveValue` (the raw solved `θ`) and `mlu` (`max(linkUtilizations.values())`, computed independently from the reported per-link loads) are mathematically identical for a correctly-built OPT model and are cross-checked against each other by `test_e_objective_value_matches_mlu` — kept as two fields rather than one so a future mode whose objective isn't literally the MLU doesn't have to overload this field's meaning.

**Status/message wording follows Part K exactly:** `INFEASIBLE` (a demand's source/target are disconnected in the effective graph — §N/§G2 test cases) is never conflated with a successfully solved `OPTIMAL` result whose `objectiveValue` happens to exceed 1.0 (congestion is unavoidable, but a routing exists and is provably the best possible — `test_k_known_congestion_example_opt_above_one` pins this down explicitly). A demand referencing a node id absent from the network entirely is treated as a **third**, distinct case — `ERROR`, a malformed request, not a topology fact — since silently treating it as "just another disconnected demand" would misreport a data bug as a network-design finding.

**API surface — deliberately narrower than §8's PR1 table row:** no `POST /optimize` route and no `optimization_service.py` were added in this PR, per this PR's own explicit instruction ("No REST endpoint yet unless architecture requires it"). `solve_unrestricted_optimum` is a plain internal function, callable directly (as the test suite does) or by a future service layer — nothing about its design presumes a particular caller. §8's table row is not corrected here since a REST route remains entirely reasonable for a *later* PR to add; this addendum simply records that PR1 did not add one.

**Frontend:** untouched. No optimization page, button, type, or API call was added — the Simulation workflow is byte-identical to before this PR.

**Tests:** `backend/tests/test_unrestricted_optimizer.py`, 18 new tests (single/multi-commodity, flow conservation, capacity constraints, objective-vs-MLU cross-check, a known-optimum case where OPT's proportional split strictly beats an ECMP-style equal split, disconnected/separate-component infeasibility, tied equal-capacity paths, a runtime smoke test, square-topology and known-congestion validation networks, the undirected shared-capacity-pool regression above, directed-link reverse-blocking, malformed-demand `ERROR` handling, empty-demand-set and self-loop-demand edge cases, and DOWN-link exclusion). Full backend suite: 184 passed (166 pre-existing + 18 new), zero regressions.

**Known limitations, left for later PRs:** (1) no REST endpoint, by design (above); (2) `flowAssignments`' path decomposition is not guaranteed unique when a demand's optimal flow has more than one valid decomposition into paths (any valid decomposition is returned — this matches Part J's own noted caveat that this reconstruction "is not always unique/deployable"); (3) `optimalityGap`/`lowerBound` are only ever `0.0`/`objectiveValue` or `None` in this PR, since OPT's pure LP never actually exercises the branch-and-bound gap machinery those fields exist for — a future exact-MILP mode (PR3) is the first real test of that part of the contract; (4) no performance testing beyond the smoke test in `test_i_runtime_smoke_test` was done on larger topologies.

## 13. Addendum — PR2 implemented Waypoint Optimization (WPO)

**This addendum records what PR2 actually built. It does not rewrite §5/§6.3/§9's own analysis — those sections remain the accurate record of the reasoning at the time they were written, including the specific tension this addendum resolves.**

**The routing-model choice, made explicit rather than silently picked:** §5/§6.3/§9 above identified two independently-complete, incompatible candidate models for waypoint optimization in the literature — [Parham21]'s `WPO`, defined over even-split ECMP routing between consecutive waypoints, and [Le21]'s `P0`, a complete, exact MILP over single-shortest-path, **unsplittable** routing between waypoints — and left the choice open pending PR0. §11's addendum then recorded that PR0, as actually implemented, upgraded Sprint 1's Segment Routing simulator to ECMP-within-segments, i.e. [Parham21]'s model, not [Le21]'s. **PR2 optimizes under exactly that same model, for the same reason PR0 chose it**: whatever PR2 recommends must reproduce identically when written back into a `SegmentRoutingPolicy` and re-simulated by the real `SegmentRoutingAlgorithm` — this is verified directly, not assumed (`test_m_optimizer_matches_sr_simulator_for_recommended_waypoint`, plus the dedicated ECMP-before/after/both-legs cross-validation tests `test_j`/`test_k`/`test_l`, all comparing the optimizer's own link loads against the real simulator's link loads to float tolerance). **[Le21]'s `P0` is deliberately not implemented in this PR** — its routing semantics no longer match Sprint 1's simulator contract after PR0's own decision — and is recorded here as a possible, separately-scoped future mode (`UNSPLITTABLE_SR_MILP`) rather than code.

**Search architecture — two strategies, chosen automatically by candidate-space size:**
- `EXACT_ENUMERATION`: a genuinely exhaustive brute-force search over the Cartesian product of every demand's own candidate-waypoint list (`None` plus every other node reachable both from the demand's source and to its destination on that demand's TE-policy-adjusted graph). Every candidate combination is scored by the shared evaluator below and the best-MLU one is kept. Deliberately never called "MILP" — no integer program is built; this is plain enumeration plus the same routing evaluator every candidate shares. `provenOptimal=True` — genuinely exhaustive within the declared candidate space (not a claim about waypoint counts beyond 1, which V1 does not search).
- `GREEDY_WPO`: [Parham21]'s Algorithm 3, followed as written — demands processed in descending order of size; for each, every candidate waypoint is tried against the current (partially-decided) assignment, and the best is kept only on a **strict** MLU improvement over `None`/the previously-kept choice (a tie never displaces the simpler option — matching the paper's own "`U_min` only updates on improvement" rule). `provenOptimal=False`, always — this is a polynomial heuristic with no optimality guarantee, and is never labeled `OPTIMAL` in `status` (it is `FEASIBLE`, per Part K's own status table).

**Search-space guard:** `search_space_size = Π(len(candidates) per demand)` is computed *before* running any search. Default ceiling `DEFAULT_MAX_EXACT_COMBINATIONS = 50_000` (`waypoint_optimizer.py`'s own constant, chosen — not from either paper — because a handful of demands over this project's teaching-scale topologies keeps the exact search near-instant, while a pathological input falls back to `GREEDY_WPO` automatically rather than hanging); exceeding it switches `searchMethod` to `GREEDY_WPO` and appends a `debugInfo` note explaining why. `test_r_search_space_guard_triggers_greedy_fallback` exercises both directions of this switch on the same topology.

**Shared routing evaluator (`waypoint_evaluator.py`):** `evaluate_waypoint_assignment(network, demands, demand_graphs, demand_required_waypoints, link_map, assignment)` routes every demand under a candidate waypoint assignment using PR0's own `compute_ecmp_leg_distribution` per leg (waypoints resolved as `[source] + segments + [target]`, each leg's `link_loads` summed directly into the running totals — precisely the "aggregate re-mixes fully at every waypoint" semantics `segment_routing.py`'s own module docstring documents) and returns link loads/utilizations/MLU. Deliberately builds no trace events, no `PathShare` Cartesian product, and does not import `segment_routing.py` at all — a search evaluating thousands of candidates does none of that per-candidate work. Written to be reused, unmodified, by a future Joint-optimization PR exactly as §8's original plan anticipated.

**TE-policy behavior:** `FORBID_LINK` and `AVOID_LINK`/`PREFER_LINK` are applied through the existing, already-reusable `te_policy.build_demand_policy_graph` (option A of this PR's own two listed options) — computed once per demand per optimization run (TE policies are static across every candidate a run evaluates, unlike the per-candidate waypoint choice itself), not re-applied per candidate. `REQUIRE_WAYPOINT` is a hard constraint the optimizer must never route around: the interaction rule adopted (the simpler of the two options this PR's own spec offered, and mathematically equivalent to the other) is that a demand with an active `REQUIRE_WAYPOINT` has its one-waypoint (V1) budget already consumed by that requirement — its own candidate list collapses to `[None]`, meaning the optimizer never adds a second waypoint on top of a required one, while the required waypoint itself is still always applied underneath (`test_i_require_waypoint_respected`). Persistent `DOWN` links are excluded identically to every other algorithm (`GraphBuilder.build_graph`'s existing exclusion, reused unchanged — `test_g_down_link_excluded_from_optimization`). Scheduled mid-simulation failures (PR 6) are explicitly out of this PR's scope, per its own instruction — WPO optimizes against one static, currently-effective topology snapshot, never across time.

**Result contract:** additive-only changes to PR1's `OptimizationResult` (all new fields `Optional`, defaulting to `None`/empty, so every PR1 OPT test and call site is unaffected — `test_t_pr1_opt_still_works_after_pr2_model_changes` pins this down): `mode` widened to include `"WAYPOINT_OPTIMIZATION"`; new fields `recommendedWaypoints` (`List[WaypointAssignmentEntry]`, one entry per routable demand, `waypointNodeId=None` itself a valid recommendation), `baselineMLU`, `optimizedMLU`, `improvement` (`baselineMLU - optimizedMLU`), `searchMethod`, `searchSpaceSize`, `evaluatedCandidates`, `provenOptimal`. `status` is `"OPTIMAL"` for `EXACT_ENUMERATION`, `"FEASIBLE"` for `GREEDY_WPO` — never the reverse — matching Part K's own OPTIMAL-vs-FEASIBLE distinction at the WPO-specific level. `message` follows this PR's own required exact phrasing ("Optimal waypoint assignment within the configured candidate space." / "Heuristic waypoint assignment (GreedyWPO) — not proven optimal.").

**OPT-as-lower-bound relationship:** not wired into `optimize_waypoints` itself (kept out of the production code path, per this PR's own "optionally reference internally... but do not build comparison UI yet" instruction) — instead verified directly in tests (`test_s_opt_lower_bounds_wpo`: `solve_unrestricted_optimum(network).mlu <= optimize_waypoints(network, config).mlu` within float tolerance, on a topology where the gap is non-trivial, not merely a coincidental equality).

**API surface:** `optimize_waypoints(network, config, max_waypoints_per_demand=1, max_exact_combinations=50_000) -> OptimizationResult` — a plain internal function, no REST endpoint (same deliberate scope narrowing as PR1's `solve_unrestricted_optimum`). `max_waypoints_per_demand` only accepts `1` in this PR (raises `ValueError` otherwise) — kept as an explicit parameter rather than a hidden constant so a future PR widening V1's single-waypoint scope changes this function's body, not its signature.

**Frontend:** untouched — no optimization page, button, or type was added.

**Tests:** `backend/tests/test_waypoint_optimization.py`, 20 new tests covering the full A–T list this PR specified (no-beneficial-waypoint, single beneficial waypoint, exact-enumeration global optimum among 3 candidates, multiple independent demands, deterministic candidate ordering, unreachable-waypoint exclusion, DOWN-link/FORBID_LINK/REQUIRE_WAYPOINT respect, ECMP-within-segments before/after/both legs with direct SR cross-validation, general optimizer-vs-simulator equality, GreedyWPO demand ordering and strict-improvement-only logic with a hand-derived order-dependent scenario, `provenOptimal` correctness for both search methods, the search-space guard triggering in both directions, `OPT <= WPO`, and a PR1-regression check on the shared `OptimizationResult` model). Full backend suite: 204 passed (184 pre-existing + 20 new), zero regressions. Frontend: `npx tsc --noEmit` and `npm run build` both clean (no sample-JSON validation script exists in this repo to run).

**Known limitations, left for later PRs:** (1) V1 supports at most one additional waypoint per demand, matching [Parham21]'s own primary analysis case — a `W>1` mode would need both a wider candidate space (combinatorial in `W`) and a decision on whether `GREEDY_WPO` extends per-waypoint or jointly; (2) `GREEDY_WPO`'s tie-break (alphabetically-first candidate wins) is a documented, deterministic convention, not something either paper specifies; (3) OPT is not exposed as a field on the WPO result itself (see "OPT-as-lower-bound relationship" above) — a future PR that wants to surface a live gap-to-OPT number in product copy will need to call both explicitly; (4) no performance testing beyond the search-space-guard tests was done on large topologies — `GREEDY_WPO`'s own runtime is `O(demands × candidates)` evaluator calls, each a handful of Dijkstra calls, which should scale comfortably but was not benchmarked here.

## 14. Addendum — PR3 implemented Link Weight Optimization (LWO)

**This addendum records what PR3 actually built. It does not rewrite §3.1/§6.2/§7.2's own analysis, or Revision 1 Part C4 — those remain the accurate historical record of the NP-hardness argument this PR is built on.**

**NP-hardness, reconfirmed, not re-litigated:** [Fortz00] §II.B/§I.D (Revision 1 Part C4, §6.2 above) proves finding an optimal OSPF/ECMP weight setting is NP-hard, because ECMP's even-split-under-variable-weights condition is not linear and shortest-path membership is itself a function of the weight variables being solved for. **This PR makes no exact-MILP claim for arbitrary topologies whatsoever** — `EXACT_ENUMERATION` is a genuinely exhaustive brute-force search, but only ever over an explicitly bounded space (a small integer weight domain raised to the power of the network's own, typically small, editable-link count); its `provenOptimal=True` is scoped precisely to "optimal within the configured weight range," never "the NP-hard problem, solved exactly, in general." `HEURISTIC_LWO` is this PR's practical fallback, in the same spirit as [Fortz00]'s own `HeurOSPF` being the literature's answer to the same intractability — but it is a simplified, deterministic hill-climb (single-link moves only, no randomized restarts or tabu search, per this PR's own explicit "no randomness in V1" constraint), not a reproduction of `HeurOSPF` itself, and this PR does not claim otherwise anywhere in code or messaging.

**Shared-ECMP-engine guarantee:** `lwo_evaluator.py`'s `evaluate_link_weights` routes every demand using the exact branch structure `ecmp.py`'s own `_route_demand` does — a hard `REQUIRE_WAYPOINT` forces a single route via `resolve_segment_route`; otherwise every equal-cost shortest path is found via `resolve_equal_cost_paths` and split evenly via `compute_ecmp_leg_distribution` (a demand with no waypoint is exactly one leg) — with `FORBID_LINK`/`AVOID_LINK`/`PREFER_LINK` applied via the same `build_demand_policy_graph` ECMP itself calls. This is verified, not assumed: `test_l_optimizer_matches_ecmp_simulator_for_recommended_weights` and `test_l2_...on_baseline` cross-validate the evaluator's link loads/utilizations/MLU against a real `ECMPAlgorithm.run()` call, both for the optimizer's own recommendation and for the untouched baseline weights. Per-demand custom `TrafficDistribution` overrides (a simulation-time visualization refinement, not a network property) are deliberately not modeled — LWO always evaluates under plain, equal-split ECMP, documented as a known limitation below, not a silent gap.

**Search architecture — two strategies, chosen automatically by candidate-space size:**
- `EXACT_ENUMERATION`: brute-force over `weight_domain ^ (optimizable link count)` — only links currently UP are ever candidates for a weight change (a DOWN link carries no traffic regardless of weight, so it simply keeps its existing weight through both `baselineWeights` and `recommendedWeights`). Deterministic: `itertools.product` iterates over sorted link ids and the ascending domain, "first encountered wins" on ties. `provenOptimal=True`.
- `HEURISTIC_LWO`: deterministic hill-climbing/coordinate descent — each round scans every optimizable link and every domain value, keeping only the single globally-best **strict** MLU improvement this round (matching PR2's `GreedyWPO` "improvement, never a tie" rule), applying it, and restarting the scan; stops the first round no single-link move improves MLU at all (a genuine local optimum under single-link moves). `provenOptimal=False`, always. `test_d2_heuristic_can_get_stuck_where_exact_succeeds` is a deliberately-included honest test: on a topology where escaping the baseline requires changing two links at once, the heuristic finds nothing while exact enumeration (same topology, `test_c`) finds the real improvement — a genuine, documented limitation of single-coordinate local search, not a bug.

**Never regresses:** unlike PR2's WPO (where `None` is always a per-demand candidate, so the search structurally cannot regress), `EXACT_ENUMERATION`'s domain may not even contain the network's actual current weights, so its own best in-domain find is explicitly compared against the untouched baseline after the search completes, and the better of the two is what's actually recommended (`optimize_link_weights`'s own docstring spells this out). `HEURISTIC_LWO` never needs this — it starts from baseline and only ever accepts strict improvements — but the comparison is applied uniformly to both search methods for one clear, single guarantee.

**Search-space guard:** default ceiling `DEFAULT_MAX_EXACT_COMBINATIONS = 50_000` (same value as PR2's WPO guard, for consistency) — chosen because it keeps exact search practical up to roughly 6 editable links at the default 1..5 domain (5^6=15,625; 5^7=78,125 already exceeds it), comfortably covering this project's small teaching topologies, while automatically falling back to `HEURISTIC_LWO` rather than hanging on anything larger. `test_e_threshold_switching_both_directions` exercises both directions of the switch on the same topology.

**Weight domain:** configurable integer range via `min_weight`/`max_weight` (default `1..5`, matching this PR's own explicit default), applied identically to both search methods.

**TE-policy behavior, failure support:** `FORBID_LINK`/`AVOID_LINK`/`PREFER_LINK`/`REQUIRE_WAYPOINT` are all applied through the exact same `build_demand_policy_graph`/`resolve_segment_route` calls `ecmp.py` itself uses — no new semantics invented (`test_g`–`test_i`). Persistent `DOWN` links are excluded identically to every other algorithm via `GraphBuilder`, and are never candidates for a weight change (`test_j`). Scheduled mid-simulation failures (PR 6) are out of scope — LWO is static, single-snapshot, exactly like PR2's WPO.

**Result contract:** additive-only extension of the shared `OptimizationResult` (all new fields `Optional`, defaulting to `None`, so every PR1/PR2 result and test is unaffected — `test_m_pr1_and_pr2_unaffected_by_pr3_model_changes` pins this down): `mode` widened to include `"LINK_WEIGHT_OPTIMIZATION"`; `searchMethod`'s type widened to also include `"HEURISTIC_LWO"` (renamed from `WaypointSearchMethod` to the mode-agnostic `SearchMethod`, since `"EXACT_ENUMERATION"` is now genuinely shared between WPO and LWO); new fields `recommendedWeights`/`baselineWeights` (`Dict[linkId, weight]`). `baselineMLU`/`optimizedMLU`/`improvement`/`searchSpaceSize`/`evaluatedCandidates`/`provenOptimal` are the exact same fields PR2 already added — reused verbatim, not duplicated under LWO-specific names, since their meaning is identical across both modes.

**OPT relationship:** verified in tests only (`test_k_opt_lower_bounds_lwo`: `solve_unrestricted_optimum(network).mlu <= optimize_link_weights(network, config).mlu`, on a topology with a genuine, non-trivial gap), not wired into `optimize_link_weights` itself — same deliberate scope narrowing as PR2's own OPT-relationship handling.

**WPO relationship:** entirely independent — `waypoint_optimizer.py` is untouched by this PR (`test_m` also asserts a plain WPO call still round-trips correctly against the widened shared model). No Joint composition of LWO+WPO is implemented; that remains PR5's explicitly scoped work per §8's table.

**API surface:** `optimize_link_weights(network, config, min_weight=1, max_weight=5, max_exact_combinations=50_000) -> OptimizationResult` — a plain internal function, no REST endpoint, matching PR1's and PR2's own scope narrowing.

**Frontend:** untouched — no optimization page, button, or type was added.

**Tests:** `backend/tests/test_lwo_optimization.py`, 15 new tests (single demand with known congestion, multiple demands, exact enumeration finding the global in-domain optimum, a genuine single-move heuristic improvement case *and* an honest single-move-insufficient case where only exact search succeeds, both directions of the search-space-guard switch, determinism across repeated calls, FORBID_LINK/REQUIRE_WAYPOINT/AVOID_LINK/PREFER_LINK compatibility, DOWN-link exclusion from the weight domain, `OPT <= LWO`, two direct ECMP-simulator cross-validations — one for the optimizer's recommendation, one for the untouched baseline — and a PR1/PR2 regression check). Full backend suite: 219 passed (204 pre-existing + 15 new), zero regressions.

**Known limitations, left for later PRs:** (1) per-demand custom `TrafficDistribution` overrides are not modeled — LWO always assumes plain equal-split ECMP, as noted above; (2) `HEURISTIC_LWO`'s single-link-move-per-round design can get stuck short of the true (even in-domain) optimum, as `test_d2` deliberately demonstrates — a multi-link joint move or a smarter escape mechanism (e.g. simulated annealing) is future work if this proves limiting in practice, but is explicitly out of this PR's "no randomness in V1" scope; (3) OPT is not exposed as a field on the LWO result itself, matching PR2's own choice; (4) no performance testing beyond the search-space-guard tests was done on large topologies.

## 15. Addendum — PR4 implemented Joint Optimization

**This addendum records what PR4 actually built. It does not rewrite §5's own analysis of the Joint MILP gap — that remains the accurate historical record this PR is built on.**

**A correction to §8's/§9's own prior anticipation, worth stating plainly:** §8's PR5 table row and §9's "Joint naming risk" DECIDE-NOW item both anticipated that Sprint 2's eventual Joint mode would necessarily be "a Sprint-2-specific hybrid... LWO(ECMP)+WPO(single-path)... NOT literally [Parham21]'s Joint," because Revision 2 (written before PR0) still expected WPO to be built over [Le21]'s unsplittable model. **That anticipation no longer applies.** PR0 chose Parham-style ECMP-within-segments for Segment Routing itself, and PR2's WPO followed suit (§11's addendum) — so this Joint implementation composes LWO(ECMP) with WPO(ECMP), the *same* routing model throughout. This means PR4's Joint mode **is** faithful to [Parham21]'s own Joint definition (weights and waypoints jointly chosen, even-split ECMP routing throughout) — a positive correction, recorded here rather than silently rewriting §8/§9's own (accurate-at-the-time) reasoning.

**No new routing model, as required:** `joint_evaluator.py`'s `evaluate_joint_assignment` composes three already-existing pieces — `lwo_evaluator.apply_weights` (PR3), `te_policy.build_demand_policy_graph` (shared since Sprint 1), and a newly-extracted `waypoint_evaluator.route_demand_with_waypoints` (PR2's own per-demand ECMP-within-segments routing step, pulled out into its own function via a pure, behavior-preserving refactor so both `evaluate_waypoint_assignment` and PR4's evaluator call the *identical* code, not two copies of it). No fourth routing engine was written.

**No duplicated search algorithms:** `waypoint_optimizer._exact_enumeration`/`_greedy_wpo` and `lwo_optimizer._exact_enumeration`/`_heuristic_lwo` each gained one new, fully backward-compatible optional parameter — `evaluate_fn` — defaulting to exactly their PR2/PR3 behavior when omitted (every existing call site, and every PR2/PR3 test, including the two that import and call `_greedy_wpo`/`_candidate_waypoints_for_demand` directly, needed zero changes and still pass unmodified — `test_n2` in this PR's own suite additionally re-confirms both public functions' default behavior). `joint_optimizer.py` calls these same four functions directly, passing a closure over `evaluate_joint_assignment` (with the *other* dimension held fixed) as `evaluate_fn` — the brute-force/hill-climbing/greedy algorithms themselves are defined exactly once each, anywhere in the codebase.

**Alternating strategy (`JOINT_ALTERNATING`, the default for any realistic network):** each round, first re-optimizes weights holding the current waypoint assignment fixed (via `lwo_optimizer`'s own exact/heuristic search, per that round's own sub-space size vs. `max_exact_combinations`), then re-optimizes waypoints holding the *new* weights fixed (via `waypoint_optimizer`'s own exact/greedy search, same per-round dispatch). Stops the first round whose combined MLU improvement drops below `epsilon`, or after `max_iterations` rounds. This generalizes [Parham21]'s own `JOINT-Heur` (Algorithm 2: run `HeurOSPF`, run `GreedyWPO` under the resulting weights, re-split demands at the chosen waypoints, re-run `HeurOSPF` — a *fixed* 3-step composition) into an iterate-to-convergence loop, per this PR's own explicit stop-condition requirement — a documented generalization, not a literal reproduction of Algorithm 2's fixed step count. `provenOptimal=False`, always, even when an individual round's own LWO or WPO step happened to run in its own exact sub-mode — alternating/coordinate-descent optimization of a jointly non-convex problem is never provably jointly optimal.

**Exact mode (`EXACT_JOINT_ENUMERATION`):** a new, but intentionally trivial, nested Cartesian product — `weight_domain ^ optimizable_link_count` combinations, each times every waypoint-assignment combination — evaluated via `evaluate_joint_assignment` directly (no existing search function to reuse here, since simultaneous double enumeration isn't what either single-dimension search does). Never called "MILP," consistent with every other exact-enumeration mode in this codebase, and consistent with §5's finding that no exact Joint MILP exists in any of our sources at all. Because this combined space is the *product* of two already-nontrivial spaces, it is realistically teaching-scale-only — `test_g_exact_joint_enumeration`'s fixture (a 4-link diamond, 1 demand) has a combined space of 1,875, comfortably under the shared default ceiling of 50,000 (`DEFAULT_MAX_EXACT_COMBINATIONS`, same value as PR2/PR3 for consistency); most realistic multi-link, multi-demand networks will exceed it quickly and fall back to `JOINT_ALTERNATING` automatically (`test_i` exercises both directions of this switch).

**Initialization:** always the network's actual current link weights and no additional waypoint per demand (never random) — matching PR2's/PR3's own conventions and this PR's explicit requirement.

**Never regresses:** the final result (from either search mode) is always compared against this same starting configuration, and the better of the two is recommended — the same safety net LWO introduced in PR3, extended here to the combined (weights, waypoints) state.

**Result contract:** additive-only. `mode` widened with `"JOINT_OPTIMIZATION"`; `searchMethod` widened with `"EXACT_JOINT_ENUMERATION"`/`"JOINT_ALTERNATING"`; two new fields, `iterations` and `convergenceReason` (both `None` for every PR1/PR2/PR3 result — `test_n` confirms this). Every other field (`recommendedWeights`, `recommendedWaypoints`, `baselineMLU`, `optimizedMLU`, `improvement`, `searchSpaceSize`, `evaluatedCandidates`, `provenOptimal`) is reused verbatim from PR2/PR3, not duplicated under Joint-specific names.

**Relationship tests:** `OPT <= Joint <= min(WPO, LWO)` (Eq. 2.1) is verified directly — not as one single scenario claiming Joint always strictly beats both (the inequality is a weak one; nothing in the literature claims otherwise), but as two separate, sharper illustrations of *why* each reuse dimension matters: `test_e_joint_le_wpo` uses a single-demand topology where the truly best route needs, in effect, two chained routing decisions that V1's one-waypoint-per-demand WPO cannot express, but which weight adjustment alone can (Joint recovers WPO's real limitation: 3.333 -> 1.0); `test_f_joint_le_lwo` uses a two-demand-same-OD-pair topology where LWO's single global weight setting cannot route the two demands onto different detours the way per-demand waypoints can (Joint recovers LWO's real limitation: 0.8 -> 0.667). `test_d_joint_ge_opt` checks the lower-bound side across all three fixtures.

**TE-policy behavior, failure support:** identical to WPO's/LWO's own (`build_demand_policy_graph` for FORBID_LINK/AVOID_LINK/PREFER_LINK, `REQUIRE_WAYPOINT` consuming the demand's one-waypoint budget exactly as WPO's own rule states) — no new semantics. DOWN links excluded via `GraphBuilder`, never optimizable. Scheduled mid-simulation failures out of scope — Joint is static, exactly like WPO/LWO.

**API surface:** `optimize_joint(network, config, min_weight=1, max_weight=5, max_exact_combinations=50_000, max_iterations=10, epsilon=1e-6) -> OptimizationResult` — a plain internal function, no REST endpoint, matching PR1-3's own scope narrowing.

**Frontend:** untouched.

**Tests:** `backend/tests/test_joint_optimization.py`, 15 new tests covering the full task list (single demand, multiple demands, joint-better-than-baseline, `OPT<=Joint`, `Joint<=WPO` and `Joint<=LWO` each with a sharp, non-trivial gap, exact joint mode, heuristic/alternating joint mode, both directions of the threshold switch, determinism, FORBID_LINK/REQUIRE_WAYPOINT compatibility, DOWN-link exclusion, and two regression checks — one confirming PR1/PR2/PR3 results are unaffected by the widened shared model, one re-confirming WPO's/LWO's own public-API default behavior is unaffected by the `evaluate_fn` refactor). Full backend suite: 234 passed (219 pre-existing + 15 new), zero regressions.

**Known limitations, left for later PRs:** (1) `EXACT_JOINT_ENUMERATION`'s combined search space grows as a product of two already-nontrivial spaces, so it realistically only ever fires on very small networks — most real use will run `JOINT_ALTERNATING`; (2) the alternating loop's own convergence is not proven to reach even the best *reachable-by-alternation* point (coordinate-descent-style optimization can converge to a different local optimum depending on which dimension is optimized first each round — this PR always does LWO-then-WPO per round, per the task's own specified order, and does not try the reverse order or a smarter interleaving); (3) OPT is not exposed as a field on the Joint result itself, matching PR2's/PR3's own choice; (4) no performance testing beyond the threshold-switch tests was done on large topologies — each alternating round costs one full LWO sub-search plus one full WPO sub-search, so runtime scales roughly additively in the number of iterations actually taken.
